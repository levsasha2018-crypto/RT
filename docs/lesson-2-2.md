# Занятие 2.2 — управление ходом исполнения ВПО

Одна прошивка `221-command-time` выполняет задания 2.2.1–2.2.5.
Версия — 1.1.0, плата — обычная Raspberry Pi Pico на RP2040, светодиод — GP25.
Кнопка в этом занятии не используется.

## Результаты настоящего прогона

Прогон выполнен 22 октября 2026 года на Pico `E66098F29B56BD32`, порт COM12.
Пять файлов `device-2-2-*.log` записаны скриптами с подключённой платы.
Вывод эмулятора в этих файлах не используется.

| Измерение | Результат |
| --- | --- |
| `clk_sys`, до смены частоты | настроено и измерено 125000 кГц |
| `clk_sys`, пониженная частота | настроено и измерено 62500 кГц |
| `clk_sys`, после восстановления | настроено и измерено 125000 кГц |
| Расчёт миллиона членов, 125 МГц | 4698 мс, π = 3.14159165 |
| Тот же расчёт, 62,5 МГц | 9397 мс |
| После восстановления 125 МГц | 4698 мс |
| Средняя итерация, 125 → 62,5 МГц | 2.57 → 5.18 мкс |
| Профилирование после долгой команды | максимум 4699093 мкс; после сброса — 292 мкс |

`clk_ref`, `clk_usb` и `clk_adc` сохранили частоты 12000, 48000 и 48000 кГц.
`uptime` на пониженной частоте шёл вровень со временем компьютера.
В логе 2.2.2 зафиксированы оба уровня светодиода и быстрые ответы на команды.

В скрипте 2.2.2 тайм-аут чтения ограничен остатком окна наблюдения.
Это сохраняет запрошенные интервалы вместо ожидания полного тайм-аута
на границе окна и уменьшает вероятность наблюдать одну и ту же фазу LED.

## Реализация

| Задание | Что сделано |
| --- | --- |
| 2.2.1 | Модуль `clock` печатает настроенные частоты через `clock_get_hz` и измеренные через аппаратный счётчик `frequency_count_khz`, включая ROSC |
| 2.2.2 | `blink` проверяет разность показаний `time_us_64`; каждые 500 мс переключает LED; суперцикл опрашивает USB без пауз; `uptime` печатает миллисекунды с запуска |
| 2.2.3 | Ряд Лейбница из миллиона членов в `double`; результат сохраняется в `volatile`; длительность измеряется непосредственно вокруг вызова |
| 2.2.4 | Модуль `profiling` измеряет каждую итерацию, хранит максимум и экспоненциальное среднее с дробной частью в целых числах; преобразование во `float` выполняется только по запросу |
| 2.2.5 | `clk_sys_low` задаёт 62,5 МГц; `clk_sys_default` возвращает `SYS_CLK_KHZ`; проверяется результат настройки PLL |

Все команды завершаются переводом строки. `info`, `version`, `ping`, `mem_info`,
`fw_info`, `dev_info` и `boot_info` сохранены из занятия 2.1.
Команды `enable` и `disable` удалены по условию нового занятия.

## Что ожидается при прогоне

- После включения: `clk_ref` — 12 МГц, `clk_sys` и `clk_peri` — 125 МГц,
  `clk_usb` и `clk_adc` — 48 МГц. Измеренные частоты должны быть близки к настроенным.
- Миллион членов ряда даёт `pi: 3.14159165`.
  Прикидка времени на 125 МГц: 585 тактов на член, около 4,68 с.
  Это оценка; фактическую длительность покажет плата.
- Во время расчёта суперцикл занят: мигание приостанавливается, команда `uptime`
  ждёт окончания расчёта. Максимальная итерация включает всё время расчёта.
- У среднего `N = 2^19`; при итерации 2 мкс память составляет около 1,05 с.
  После длительной итерации среднее возрастает, затем постепенно возвращается.
  `main_time_reset` сбрасывает максимум, сохраняя среднее.
- На 62,5 МГц расчёт должен длиться примерно вдвое дольше, итерации — стать медленнее.
  Аппаратный таймер продолжает отсчитывать микросекунды, период LED остаётся 1 с.
- Pico SDK 2.3.0 при смене частоты ядра переводит `clk_peri` на PLL USB (48 МГц).
  При возврате ядра на 125 МГц периферия остаётся на 48 МГц до перезагрузки.

## Запись логов с платы

1. Соберите проект: `./tools/build.ps1 -Project 221-command-time`.
2. Запишите файл `221-command-time/build/221_command_time.uf2` на Pico через BOOTSEL.
3. Дождитесь появления USB-порта и мигания. Дайте прошивке поработать 10 секунд,
   чтобы среднее профилирования установилось. Закройте программы, занимающие USB-порт.
4. Перейдите в папку проекта и выполните скрипты по очереди:

```powershell
cd 221-command-time
python check-2-2-1.py
python check-2-2-2.py
python check-2-2-3.py
python check-2-2-4.py
python check-2-2-5.py
```

Нажимать кнопку или замыкать контакты не требуется. Каждый скрипт сам отправляет
команды и сохраняет соответствующий `device-2-2-*.log` в текущей папке.
Перед первым скриптом плата должна работать на обычной частоте; последний скрипт
сам понижает частоту и возвращает её обратно.
Перед повторным полным прогоном перезагрузите плату и снова дайте ей поработать.

После записи проверяем логи официальными проверками, добавляем их вместе с кодом
и пятью workflow в Git, отправляем в репозиторий. GitHub Actions проверяет проект
и передаёт результаты на платформу курса через уже настроенный секрет.

## Эмуляция

Готовая UF2 запущена локально в [RP2040js](https://github.com/wokwi/rp2040js).
Проверены USB-команды, период мигания, вычисленный результат π и задержка ответа
`uptime` во время расчёта. Профилирование зафиксировало длительную итерацию.

Эмулятор выполняет ARM-прошивку, но его модель не является точным замером времени
реального RP2040. В используемой версии нет аппаратного счётчика частоты FC0,
а выполнение моделируется на фиксированных 125 МГц. Поэтому `clk_info` исключён
из локального прогона; измерения частот, ROSC и отношения времени на двух частотах
проверяются на настоящей Pico. Вывод эмулятора не записывается в файлы сдачи
`device-2-2-*.log`.
